# Scent Library

A small, installable web app for keeping track of perfumes and deciding whether a
scent suits you. Each person signs in, sets up their own taste (likes, dislikes,
flags), adds the scents they come across, and gets a rules-based **“Is this for
me?”** verdict for each one.

- **Library** of scent cards: name, brand, gender, top/heart/base notes, status
  (curious, love, fine, nope, hell no, predicted-no), have/smelled, retail price,
  where seen, your own notes, Armor/Lounge, and an optional photo you upload.
- **Verdict**: Yes / Leaning yes / Leaning no / No / Mystery, with the reason and
  the matching notes shown underneath.
- **Dupe links** between an original and its dupe: _Dupe of_, _Has DNA of_,
  _Inspired by_.
- **Bid calculator** for live auctions.
- **PWA**: add it to an iPhone home screen and it opens full-screen; the app shell
  works offline.
- **Demo mode**: with no Supabase project configured, the app runs entirely in
  the browser with a few made-up cards, so you can try it straight away.

No AI, no API keys in client code, and no data copied from perfume databases.
Users type their own notes and upload their own photos.

## How the verdict works

Rules live in [`src/domain/verdict.ts`](src/domain/verdict.ts) and are fully
tested.

| Match                       | Points                               |
| --------------------------- | ------------------------------------ |
| A note in your **likes**    | +1                                   |
| A note in your **dislikes** | −1                                   |
| A note in your **flags**    | −2 (and a flag rules out a full Yes) |
| A **lounge cue**            | 0, never negative; suggests Lounge   |

Each rule counts once. Matching is by whole word, so `musk` matches “white musk”
but `rose` does not match “rosewood”.

- no notes, or no note matches your profile → **Mystery**
- score ≥ 2 and no flags → **Yes**
- score ≥ 1 → **Leaning yes**
- score ≤ −2 → **No**
- otherwise → **Leaning no**

Flags can be marked **lead-only**: they count only in the top notes or as the
first note of a layer (useful for “oud as a lead is a no, a trace of oud is
fine”). The header and the reason are built from the same match lists, and a
test walks every combination of matches to check they never contradict.

The **My taste** page has a “Load example profile” button with a starter set of
rules that users can edit or throw away.

## Bid calculator

From [`src/domain/bid.ts`](src/domain/bid.ts):

- **max total** (bid + fees) = 60% of retail
- **max bid** = max total − $5
- **mystery bottles** are capped at a $10 bid
- if the max bid would be $0 or less, it says **skip**

## Why plain TypeScript + Vite (no framework)

The app is a handful of screens with forms and lists. A UI framework would add
a dependency to keep updated and a layer to learn, for little gain at this
size. Instead there is a ~50-line DOM helper ([`src/dom.ts`](src/dom.ts)) that
builds elements and never injects HTML strings, so user text can’t inject
markup. TypeScript catches mistakes early, and Vite gives a fast dev server and
a static `dist/` folder that GitHub Pages can serve. Runtime dependencies: just
`@supabase/supabase-js`.

## Project layout

```
index.html                    app entry, iOS home-screen meta tags
public/manifest.webmanifest   PWA manifest
public/sw.js                  service worker (offline app shell, never caches user data)
public/icons/                 generated by `npm run icons`
src/domain/                   verdict, bid and note rules (pure, unit-tested)
src/data/                     Store interface: SupabaseStore + LocalStore (demo)
src/views/                    one file per screen
src/ai/aiVerdict.ts           marked placeholder for future server-side AI (off)
supabase/migrations/          SQL schema + row-level security
supabase/tests/               RLS tests that run against a local Postgres
supabase/functions/ai-verdict placeholder notes for a future Edge Function
```

## Run it locally

Needs Node 20 or later.

```bash
npm install
npm run dev
```

Open the printed URL. With no `.env.local`, it runs in **demo mode**: press
“Try the demo”. Demo data lives only in that browser; “Reset demo” on the
My taste page wipes it.

Checks (the same ones CI runs):

```bash
npm run check
```

That runs typecheck, ESLint, Prettier (check only) and the unit tests.
`npm run build` produces `dist/`; `npm run preview` serves it, including the
service worker.

The RLS tests need Postgres binaries on your PATH (for example from Postgres.app):

```bash
npm run test:rls
```

## Set up Supabase

1. Create a free project at [supabase.com](https://supabase.com).
2. **Database schema**: open the SQL editor, paste
   [`supabase/migrations/20261111000000_init.sql`](supabase/migrations/20261111000000_init.sql)
   and run it. (Or, with the Supabase CLI: `supabase link` then `supabase db push`.)
   This creates the tables, turns on row-level security, and creates a private
   `scent-photos` storage bucket with per-user folders.
3. **Auth → Providers**: Email is on by default; magic links work with no
   extra setup. The free tier’s built-in email sender is rate-limited, so for
   more than a few users add your own SMTP under Auth → SMTP settings.
4. **Auth → URL configuration**:
   - Site URL: your Pages URL, e.g. `https://<your-github-username>.github.io/scent-library/`
   - Redirect URLs: the same URL, plus `http://localhost:5173/` for local dev.
5. **Project settings → API**: copy the Project URL and the `anon` public key.
6. Locally: copy `.env.example` to `.env.local` and fill in both values.

The anon key is designed to be public: it is shipped to every browser, and
row-level security is what keeps each person’s rows private. **Never** put the
`service_role` key in `.env.local`, GitHub variables or client code.

### Adding Google or Apple sign-in later

Enable the provider in Supabase (Auth → Providers) and follow its setup steps,
then set `VITE_AUTH_PROVIDERS=google` (or `google,apple`). The buttons appear on
the sign-in page; no code changes needed.

## Deploy to GitHub Pages

1. Create the GitHub repository and push this code (default branch `main`).
2. **Settings → Pages → Build and deployment → Source: GitHub Actions.**
3. **Settings → Secrets and variables → Actions → Variables**: add
   `VITE_SUPABASE_URL` and `VITE_SUPABASE_ANON_KEY` (and optionally
   `VITE_AUTH_PROVIDERS`). Without them the deployed site runs in demo mode.
4. Push to `main` (or run the workflow by hand). The workflow in
   [`.github/workflows/deploy.yml`](.github/workflows/deploy.yml) runs the checks,
   builds with the right base path (`/<repo-name>/`) and publishes.

### Add to an iPhone home screen

Open the site in Safari → Share → **Add to Home Screen**. It then opens
full-screen like an app.

## Security notes

- Every table has `user_id` defaulting to the signed-in user, and RLS policies
  allow reading or writing only rows where `user_id = auth.uid()`. Signed-out
  visitors have no access.
- Dupe links use composite foreign keys, so a link can only join two of the
  same user’s own cards.
- Photos go to a private bucket under `<user_id>/…`, are shown through
  one-hour signed URLs, and are resized in the browser first (which also strips
  EXIF data such as GPS location).
- The service worker caches only the app’s own files, never Supabase responses.

## Future: AI verdicts

Not in this version. The marked spot is [`src/ai/aiVerdict.ts`](src/ai/aiVerdict.ts),
with notes in [`supabase/functions/ai-verdict/`](supabase/functions/ai-verdict/README.md).
Any AI call must go through a server-side function so the model key stays in
Supabase secrets.

## Content rules

- Do not seed the app with note lists, descriptions or images copied from
  perfume databases or retailers; their terms usually forbid it.
- The demo cards in `src/data/demoData.ts` are invented.
- Users upload only photos they took themselves.
